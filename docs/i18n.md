# Languages (DIVASTRO-121)

Divine Astro speaks English and Hindi fully, and has the plumbing for Kannada
(kn), Telugu (te), Tamil (ta), Malayalam (ml), Bengali (bn) and Odia (or).
Everything about a language lives in **`app/i18n.py`** (`LANGUAGES`): code,
native name, English name, script, hreflang/BCP-47, `og:locale`, URL prefix
(`""`, `/hi`, `/kn`, ...), `status` (`full` / `beta`), the Google Fonts family
for its script, and the few short strings that must be readable before
anything is translated (picker heading, first-visit hint, "translation coming
soon" notice) — written in each language's own script.

English is the fallback everywhere, per string.

## The rule for search engines

A page whose body is still English must not be indexed as Kannada. Every
server-rendered module declares the languages it has really been written in:

```python
TRANSLATED = i18n.BASE_TRANSLATED          # frozenset({"en", "hi"})
```

| | language in the module's `TRANSLATED` | not (yet) in it |
|---|---|---|
| `/kn/...` renders | yes, in Kannada | yes, English body + `<html lang="kn">` |
| `<meta name="robots">` | — | `noindex, follow` |
| hreflang alternates | listed on every copy | none; not listed by the others |
| sitemap.xml | listed | left out |
| "translation coming soon" note | — | shown, in Kannada script |

So translating a module is: write the text, add the code to `TRANSLATED`.
hreflang, sitemap, noindex and the notice follow from that one set.

Modules and their sets:

| module | pages | `TRANSLATED` |
|---|---|---|
| `app/seo_pages.py` | /panchang, /rahu-kaal, /choghadiya (+ ~110 cities), /kundali-milan, /free-kundali | `seo_pages.TRANSLATED` |
| `app/rashifal_pages.py` | /rashifal, /rashifal/<sign> | `rashifal_pages.TRANSLATED` |
| `app/vrat_pages.py` | /vrat-tyohar[/<year or city>], /ekadashi-<year>, /tyohar/<slug>-<year> | `vrat_pages.TRANSLATED` |
| `app/nakshatra_pages.py` + `app/naam_milan.py` | /nakshatra[/<x>], /rashi[/<x>], /naam-se-kundali-milan | `nakshatra_pages.TRANSLATED` |
| `app/muhurat_pages.py` | /muhurat/<kind>-<year> | `muhurat_pages.TRANSLATED` |
| `app/katha.py` | /katha (Hindi, canonical), /en/katha | `katha.TRANSLATED` — **no /kn/katha routes yet**; the picker sends other languages to /en/katha |

The five modules above are `BASE_TRANSLATED | {"ta", "ml"}` (DIVASTRO-123).

The `/kn/...` routes are generic: `/{lang:xlang}/panchang` etc., where the
`xlang` path convertor (registered in `i18n.py`) matches exactly
`i18n.EXTRA_CODES`. English and Hindi keep their own routes.

## Translating a server-rendered module into, say, Kannada (DIVASTRO-123)

Every server-rendered page has **one builder that takes `lang`**; there are no
`"…" if hi else "…"` branches and no separate Hindi builders. All words live in
data files next to each module, so translating is filling tables, not editing
logic:

| module (pages) | file a translator fills | tables and key counts (en / hi) |
|---|---|---|
| `seo_pages.py` (/panchang, /rahu-kaal, /choghadiya, /kundali-milan, /free-kundali) | `app/seo_text.py` | `TEXT` 134 / 125 keys (+30 `_native`); `FAQ` 7 / 7 Q&A pairs |
| `rashifal_pages.py` (/rashifal, /rashifal/<sign>) | `app/rashifal_text.py` | `TEXT` 51 / 64 (+5 `_native`); `MORE_LINKS` 6 / 6; phrase banks `TONE_LABEL` 3, `MOON_HOUSE`, `SATURN_HOUSE`, `JUPITER_HOUSE`, `RAHU_HOUSE` 12 each, `KETU_LINE` 2 (each entry `{"en", "hi"}`); `CLOCK_LANG` |
| `vrat_pages.py` (/vrat-tyohar…, /ekadashi-<year>, /tyohar/<slug>-<year>, the panchang festival box) | `app/vrat_text.py` | `TEXT` 64 / 61 (+1 `_native`); `ABOUT` 47 / 47 festival descriptions; `NOTES` 11 / 11 tradition notes |
| `muhurat_pages.py` (/muhurat/<kind>-<year>) | `app/muhurat_text.py` | `TEXT` 37 / 31 (+1 `_native`); `MONTHS` (Hindi spells फरवरी without nukta here) |
| `nakshatra_pages.py` (/nakshatra[/<x>], /rashi[/<x>]) | `app/nakshatra_page_text.py` and `app/nakshatra_text.py` | `TEXT` 88 / 88 (+1 `_native`); `NAKSHATRA_TRAITS` 27 and `RASHI_TRAITS` 12 entries, each `{"en", "hi"}` |
| `naam_milan.py` (/naam-se-kundali-milan) | `app/naam_milan_text.py` | `TEXT` 34 / 34 |
| shared chrome (crumbs, footer, share) | `i18n.CHROME` | 10 |

Also, for each regional language, four bits of data the engines only have in
en/hi, each with one per-language slot (DIVASTRO-123 — see "Regional hooks"
below): `vrat_text.RULES`, `nakshatra_text.FACTS`, the namakshar script rule in
`i18n._AKSHAR`, `astro/choghadiya.CHOGHADIYA_INFO[...]["description_<code>"]`,
plus `naam_milan_text.ENGINE` and the city/state names in
`app/seo_city_names.py`. Without an entry they stay English / Devanagari.

(hi has fewer keys where the English template already fits Hindi, e.g. `when`;
more where Hindi needs its own word forms, e.g. rashifal's `house.1`..`12`.)

1. **Strings.** Add a `"kn"` dict to the file's `TEXT` with any subset of the
   `"en"` keys; add `"kn"` entries to the other tables (`FAQ["kn"]`,
   `ABOUT["kn"]`, `MOON_HOUSE[i]["kn"]` …). Lookup is per key:
   `TEXT["kn"]` → `TEXT["_native"]` → `TEXT["en"]` (`i18n.t`). Templates are
   read with `i18n.fmt(key, lang, TEXT, **values)` — keep the `{placeholders}`
   (each file lists them above its keys), the word order is yours. Values
   marked HTML are inserted as they are (keep the tags, write `&amp;`); titles,
   descriptions and link texts are plain text.
   * Every template may also use the language's astrology labels:
     `{t_rahu_kaal}`, `{t_yamaganda}`, `{t_gulika}`, `{t_abhijit}`,
     `{t_sunrise}` … (names `TIMINGS`) and `{l_tithi}`, `{l_nakshatra}`,
     `{l_vara}`, `{l_paksha}`, `{l_moon_sign}`, `{l_panchang}` … (`LIMBS`).
     Don't name a placeholder `key`, `lang` or `table`.
   * The `"_native"` layer holds the few keys that are just an astrology name
     (`"p.r_rahu": "{t_rahu_kaal}"`), so an untranslated Kannada page already
     prints ರಾಹು ಕಾಲ there. Your `"kn"` entry overrides it.
   * Don't translate astrology names here — tithi, nakshatra, yoga, karana,
     weekday, month, rashi, graha, choghadiya, koota, festival and timing
     names come from `app/astro/names_<code>.py` (below).
   * Dates and times: `i18n.format_date(day, lang[, short=True])`,
     `i18n.format_time(moment, lang)` (part-of-day word from names `CLOCK`),
     `i18n.weekday(day, lang)` — nothing to do per language.
   * City/state names: `{city}` is the city in the page's language
     (`seo_cities.city_name`: `City.name_hi` for Hindi,
     `seo_city_names.CITIES[lang][slug]` for the regional languages, else
     English). Don't glue a case ending to it with a hyphen (`{city}-এ`,
     `{city}-இல்`): either attach it the way the script does for every name
     (Odia `{city}ରେ` works) or say "in the city of" (`{city} ನಗರದಲ್ಲಿ`,
     `{city} నగరంలో`, `{city} நகரில்`, `{city} നഗരത്തിൽ`, `{city} শহরে`).
2. **Shared chrome.** Fill `i18n.CHROME["kn"]` (Home, breadcrumb, footer links,
   disclaimer, "Share on WhatsApp"). Values are inserted as HTML: escape `&`.
3. **Flip the flag**: add `"kn"` to the module's `TRANSLATED`.
4. **Test**: `tests/test_i18n.py` section 8 shows the expected result (simulates
   it for seo_pages); its section 3 asserts the current sets — update it.
   `tests/test_seo_snapshots.py` must stay green: it pins the English and Hindi
   HTML of ~950 pages byte for byte (on a fixed date), so a change to an `"en"`
   or `"hi"` value, or to a builder, shows up there. Re-record (`--update`)
   only for an intended English/Hindi change — and adding a language to a
   `TRANSLATED` set is one: every en/hi page of that module gains the new
   hreflang line and sitemap.xml its URLs (nothing else may change).
   Snapshots cover en/hi only (the `?v=` cache-buster and "/"'s
   `window.DA_I18N_V` stamp are normalised away). The regional languages are
   checked by `tests/test_seo_regional.py` (all six, or `... kn` for one):
   complete tables in the script, the hooks below, indexable pages with
   reciprocal hreflang and sitemap entries, no English or Devanagari left in
   `<main>`, and native city names in titles, headings, breadcrumbs and
   JSON-LD. Add your language to its `ALL`, `RANGE`, `SCRIPT`, `OWN_CITIES`.

Done (DIVASTRO-123): **kn, te, ta, ml, bn, or** in all five modules above (not
katha).

### Regional hooks (one design each)

* **Deity and symbol** of each nakshatra: `nakshatra_text.FACTS[lang]` with
  `"deity.<slug>"` / `"symbol.<slug>"` for all 27, read by
  `nakshatra_pages._own` (English/Hindi stay `deity`/`deity_hi` in
  `astro/namakshar.py`).
* **Namakshar syllables** (Devanagari in `astro/namakshar.py`, and a name's
  first letter) in the reader's script: `i18n.akshar(text, lang)` and the
  `lang=""` attribute `i18n.akshar_lang(lang)`. One table, `i18n._AKSHAR`:
  `lang: (Unicode block start, per-letter overrides)`. The Brahmi scripts
  share Devanagari's layout, so a letter moves to the same offset — kn, te, ml
  one-to-one; ta folds the voiced/aspirated stops Tamil lacks (घ → க, ध → த);
  bn and or write व as ব / ବ. A letter with no counterpart stays Devanagari.
* **"How the date is fixed"**: `vrat_text.RULES[lang]` — `head` ("{month}
  (amanta) "), `tithi` ("{paksha} {tithi}: "), `rule.<kind>` for every
  `festivals.RULE_TEXT` kind and `key.<observance>` for the four observances
  that are not a tithi rule (ekadashi, makar_sankranti, lohri, holi); composed
  by `vrat_pages._rule`.
* **Choghadiya slot notes**: `description_<code>` in each
  `astro/choghadiya.CHOGHADIYA_INFO` entry (the JSON API stays en/hi).
* **Naam-milan result**: `naam_milan_text.ENGINE[lang]` (score-band and
  convention notes; the verdict word is `seo_text` `km.band<i>`). The
  per-koota notes stay the engine's English.
* **City and state names**: `app/seo_city_names.py` — `CITIES[lang][slug]`
  for all 114 cities and `STATES[lang][state]` (exposed as
  `seo_cities.STATE_<CODE>`). `seo_cities.city_name / state_name / place /
  has_name` read them, so titles, H1s, the date line, breadcrumbs (and their
  JSON-LD), city indexes and the muhurat place line are native; slugs and URLs
  never change, and en/hi output never comes from this file.

Still English on regional pages: the per-koota notes of a naam-milan result
and the WhatsApp share message (en/hi only).

**Until a module is translated**, its `/kn/...` pages render the English text
(noindex, "translation coming soon"), but every astrology name, timing label,
weekday, month, clock word and festival name already comes out in Kannada
script from `names_kn.py`.

Links inside an untranslated page are kept in the reader's language by
`i18n.localize_links` (`/panchang/pune` → `/kn/panchang/pune`, `/?open=x` →
`/?open=x&lang=kn`), for path roots a module registers in
`i18n.LOCALIZABLE_ROOTS`. A translated builder may write those links itself;
the rewrite is idempotent.

## Astrology names: `app/astro/names_<code>.py`

One loader: **`app.astro.names_i18n.names_for(lang)`** (also `i18n.names(lang)`;
`app.astro.names` is a deprecated alias). It returns a `Names` object with the
same tables for all eight languages — `TITHI`, `NAKSHATRAS`, `VARA`, `YOGA`,
`KARANA`, `PAKSHA`, `MASA`, `SOLAR_MASA`, `RASHI`, `GRAHA`, `CHOGHADIYA`,
`CHOGHADIYA_QUALITY`, `TIMINGS`, `FESTIVAL_TIMINGS`, `FESTIVALS`, `EKADASHI`,
`KOOTA`, `GANA`, `NADI`, `VARNA`, `VASHYA`, `YONI`, `TARA`, `WEEKDAY`,
`MONTHS`, `CLOCK`, `LIMBS`, the two notes — keyed by the English names the
engines emit, plus `clock()`, `festival()` / `festival_name()` and
`tithi_label()`. English and Hindi are read from names_hi / festivals /
matching / choghadiya; each regional language is `names_<code>.py` with the
tables suffixed `_KN` etc. `add_names(p, lang)` / `add_all(p)` give
`/api/panchang` its `name_<code>`, `label_<code>`, `paksha_<code>`,
`notes_<code>` fields, which the app's `loc(row, "name")` reads.

## APIs

Every `language` / `lang` parameter accepts any value and never answers 422.
The deterministic engines write English or Hindi
(`main._engine_lang`); any other code gets English. The chat narration
(`llm.LANGUAGES`) is written in all eight languages.

DIVASTRO-124, the six regional languages beyond the app strings:

* **Answers.** For kn/te/ta/ml/bn/or the engine runs in English and the model
  writes the answer in the language, with a glossary (`llm._glossary`: grahas,
  rashis, nakshatras, Rahu Kaal etc. from `names_for(lang)`, house/dasha words
  from `app/astro_terms.py`). The date auditor reads dates in every script and
  in native digits (`llm._dates_in`). With narration off or failed, the result
  carries `fallback_note` — `i18n.Language.english_answer`, "Answer shown in
  English" in that language — and the app shows it above the English text.
* **Kundali PDF** (`/api/pdf/chart`, `main._pdf_lang`): labels in
  `app/pdf_i18n.py`, fonts Noto Serif/Sans <script> (in fonts-noto-core).
  Offered languages = `pdf_report.pdf_languages()` (en, hi + every regional
  language whose font is installed), inlined as `window.DA_PDF_LANGS`. The
  yoga names/notes and the text inside the North/South Indian squares stay in
  English (Typst does not shape Indic text inside SVG). Remedies, single-question
  and Life Book PDFs remain en/hi.
* **Email / push**: `email_auth.subject()/compose()` and
  `push_message.build()` write all eight languages.

## Fonts

Hindi uses the system Devanagari fonts as before. The six new scripts load one
Noto Sans family from Google Fonts **only for the active language**
(`i18n.font_link` on server pages, `loadFont` in app.js), `display=swap`.
`styles.css` appends the script font after the Latin families in
`--sans`/`--serif` for `html[lang=kn]` etc. (generated by `i18n.font_css()`; a
test keeps them equal). The Caddyfile CSP allows `fonts.googleapis.com`
(style-src) and `fonts.gstatic.com` (font-src) — **a Caddyfile change needs a
caddy container restart to take effect.**

## The language picker

One component everywhere: `<details class="lang-picker">` — a pill with a
globe and the current language's native name, opening a list of all eight
(native name + English name). Server pages get it from `i18n.picker()` at the
top of every page; the app header from the same function via main.py.
`static/langpick.js` adds Escape/outside-click/arrow keys, remembers the choice
(`localStorage["astro.lang"]`), switches the app in place (`window.daSetLang`),
and shows the one-time first-visit hint when the browser's languages include
one of ours (`localStorage["astro.langHint"]` once dismissed).

## The app (SPA): `app/static/i18n/<code>.json`

All UI strings of app.js, account.js, tools.js, share.js and push.js are keys
in `app/static/i18n/en.json` (the source of truth) and `hi.json`. The six new
languages start as `{}`.

* main.py inlines the registry (`window.DA_LANGS`) and the English and Hindi
  tables into index.html, so first paint needs no fetch. Any other language is
  fetched once from `/static/i18n/<code>.json?v=<static version>` when chosen.
* `t(key)` falls back to English per key: a partial file is fine.
* **To translate the app into Kannada:** fill `app/static/i18n/kn.json` with
  any subset of en.json's keys. Keep `{placeholders}` (word order is yours,
  e.g. `untilTpl`), and keep the shape of the few non-string values
  (`starters`, `acct.upiHelpApps`, `acct.errors`, `acct.status`). No code
  change. When done, set the language's `status` to `"full"` in `i18n.py`.
* API names: the app reads `row["name_<code>"]` (likewise `label_`, `day_`,
  `url_`) and falls back to English — they appear once the server sends them
  (`app/astro/names_<code>.py`).
* `?lang=<code>` and `localStorage["astro.lang"]` are honoured; unknown codes → English.
* Tests: `tests/test_i18n_app.py` (JSON validity, en.json covers every `t()`
  key, Hindi unchanged against `tests/i18n_hi_baseline.json`, new files only
  use known keys); `tests/e2e/test_language_picker.py`.


## Adding a language the per-language-module way (DIVASTRO-143)

Punjabi (`pa`), Nepali (`ne`), Assamese (`as`), Marathi (`mr`) and Gujarati (`gu`) were
added so that five translators can work at once without touching a shared file. The
older six (kn te ta ml bn or) stay inline in the shared text modules; do not move them.

### File ownership

A translator of `<code>` edits exactly these three things and nothing else:

| file | what |
|---|---|
| `app/lang_data/<code>.py` | every table that is inline for kn..or: `SEO_TEXT`, `SEO_FAQ`, `CHROME`, `STAY_STRIP`, `CITY_NAMES`, `STATE_NAMES`, `CHOGHADIYA_DESC`, `RASHIFAL_*`, `VRAT_*`, `NAKSHATRA_*`, `RASHI_TRAITS`, `NAAM_MILAN_*`, `MUHURAT_*`, `RECURRING_TEXT`, `HUB_LABELS`, `ASTRO_TERMS`, `ASTRO_MONTHS`, plus `READY`, `ALLOW_LATIN`, `KEEP_ENGLISH`, `AKSHAR` |
| `app/astro/names_<code>.py` | tithi, nakshatra, vara, yoga, karana, rashi, graha, festival ... names (`TITHI_PA` ...), keyed by the English name |
| `app/static/i18n/<code>.json` | the app's strings, a subset of `en.json`'s keys (starts as `{}`) |

`app/i18n.py` (registry, short strings), the shared text modules and every test are not
touched. `as` is a Python keyword, so the modules are loaded by name with importlib
(`lang_data.load("as")`); the file is `app/lang_data/as.py` like the others and the code
stays `as`. Do not write `import as`.

### How it plugs in

Each shared module calls `lang_data.merge("SEO_TEXT", TEXT)` (one commented line next to
its tables) which overlays the language's constant into the live table at import, so
`TEXT["pa"]` exists as if written inline. `""` values are skipped: "not translated".
`names_for("pa")` fills every hole with the English name, key by key (never a KeyError).
`i18n._AKSHAR`, `CHROME` and `CHOGHADIYA_INFO` are fed the same way.

### READY flags

`READY = frozenset({"seo", "rashifal", "vrat", "nakshatra", "muhurat", "recurring", "hub", "app"})`
in the language's own file names the page modules that are complete for it:

| key | pages | tables |
|---|---|---|
| `seo` | /panchang /rahu-kaal /choghadiya /kundali-milan /free-kundali, city names | SEO_*, CHROME, STAY_STRIP, CITY_NAMES, STATE_NAMES, CHOGHADIYA_DESC |
| `rashifal` | /rashifal[/<sign>] | RASHIFAL_* |
| `vrat` | /vrat-tyohar, /ekadashi-<y>, /tyohar/... | VRAT_* |
| `nakshatra` | /nakshatra, /rashi, /naam-se-kundali-milan | NAKSHATRA_*, RASHI_TRAITS, NAAM_MILAN_*, AKSHAR |
| `muhurat` | /muhurat/<kind>-<y> | MUHURAT_* |
| `recurring` | /purnima-<y>, /amavasya-<y>, /pradosh-vrat-<y> ... (needs `vrat` clean: it reuses its keys) | RECURRING_TEXT |
| `hub` | /sitemap | HUB_LABELS |
| `app` | the SPA json, API `name_<code>` fields, AI glossary | names_<code>.py, <code>.json, ASTRO_TERMS |

Every page module's `TRANSLATED` is `BASE | legacy six | lang_data.ready(<key>)`
(`recurring_pages`, `site_hub` likewise), so flipping a module is one edit in the
translator's own file. While a key is not READY the language's pages for that module
render the English body, `noindex`, no hreflang, out of the sitemap, with the "translation
coming soon" note (the rule at the top of this document). A page-module key also needs
`names_<code>.py` clean (pages print names), and `check` + CI fail if `READY` names a
module whose tables are incomplete.

A language shows in the picker and the app's registry (`i18n.listed_codes`,
`lang_data.listed`) as soon as `READY` is non-empty, so adding the registry entries
changed nothing on any English or Hindi page. `ASTRO_LIST_ALL_LANGS=1` lists all of them
(staging, screenshots, the e2e picker test). The first READY flip adds the language to
every en/hi page's picker and hreflang/sitemap: re-record `tests/test_seo_snapshots.py`
then (`--update`) and say so in the commit.

### Skeleton and check

    python -m app.lang_data skeleton pa [--force]     # (re)write the three files
    python -m app.lang_data check pa [--only seo,names,json,akshar] [--all] [--quiet]
    python -m app.lang_data check kn --live           # the same checks on an older language

`skeleton` writes every table with every English key and value `""` (the TODO marker),
with the English text and `# keep: {placeholders}` / `# may also use:` above each key; it
refuses to overwrite a file that differs from a fresh skeleton unless `--force`.
`check` reports per table: missing, empty, extra, placeholders, same as English, wrong
script, braces, html (unbalanced tags), and READY inconsistencies; exit 0 only when
nothing is reported. Placeholders are not compared to English: its templates carry Hindi
twin helpers (`{city_hi}`), and the regional languages differ from each other. The rule:
a value must keep every placeholder that all of kn te ta ml bn or keep, and may use only
those any of them use (+ `{t_*}` / `{l_*}` astrology labels).

### Unicode blocks used for the script check

| language | block(s) |
|---|---|
| pa | Gurmukhi U+0A00-0A7F |
| gu | Gujarati U+0A80-0AFF |
| as | Bengali U+0980-09FF (contains ৰ U+09F0 and ৱ U+09F1) |
| mr, ne (hi) | Devanagari U+0900-097F |
| kn te ta ml bn or | U+0C80 / 0C00 / 0B80 / 0D00 / 0980 / 0B00 + 7F |

Only letters and marks are checked: digits, punctuation, symbols, ZWJ/ZWNJ, HTML tags,
entities, `{placeholders}`, URLs and the Latin words in `check.DEFAULT_ALLOW_LATIN`
(WhatsApp, UPI, PDF, IST, N/E, D1..D60 ...) pass; add others to the file's `ALLOW_LATIN`.
In the json, capitalised app names present in the English value (PhonePe, UTR) pass.

### names_<code>.py shape

One table per name, suffix `_<CODE>`, keyed by the English names the engines emit:
`TITHI`(16) `NAKSHATRAS`(27) `VARA`(7) `YOGA`(27) `KARANA`(11) `PAKSHA`(2) `MASA`(12) `SOLAR_MASA`
(optional, solar calendars) `RASHI`(12) `GRAHA`(9) `CHOGHADIYA`(7) `CHOGHADIYA_QUALITY`(3)
`TIMINGS`(15) `FESTIVAL_TIMINGS`(32) `FESTIVALS`(57) `EKADASHI`(26) `REGIONAL_NOTE`(optional)
`KOOTA`(8) `GANA` `NADI` `VARNA` `VASHYA` `YONI` `TARA` `WEEKDAY`(7) `MONTHS`(list of 12)
`CLOCK`(4, `late_afternoon` optional) `LIMBS`(10), strings `NOTE_POLAR`, `NOTE_WEDNESDAY`, and
`add_<code>(p)`. See names_bn.py for a finished one. Document choices for the native
reviewer in the module docstring.

### The app json

`static/i18n/<code>.json` is a flat object with a subset of `en.json`'s keys (nested
`starters`, `acct.upiHelpApps`, `acct.errors`, `acct.status` keep their shape). `{}` means
English everywhere. `check` compares against `en.json`. When complete set `"app"` in READY
and `status` to `"full"` in `i18n.py` if the owner wants the beta label gone.

### Not covered by lang_data (English today for the five)

`pdf_i18n` (PDF labels; `main._pdf_lang` sends the five English and the picker hides
them), `email_auth` and `push_message` (English + Hindi text), the WhatsApp share text,
learn pages (en/hi only, hidden). The AI narration is in all five from day one
(`llm.LANGUAGES`, `llm.REGIONAL`); its glossary turns on with READY `app`.
